I feel like we've gradually made the coordination layer, documentation, and agent contract much more complex, and I'm worried that this is actually making the agent use the MCP *less*, not more.

I don't want us to start deleting or rewriting things based on intuition.

Instead, I want us to properly research this.

Research how successful MCP servers, AI agent frameworks, Claude Code, Cursor, OpenCode, and similar systems structure their documentation, agent rules, and workflows.

Questions I want answered:

- How much documentation should an MCP expose to an agent?
- Should the primary workflow be very short, with deeper docs only when needed?
- How do successful MCPs guide agents without overwhelming them?
- Should the contract look more like a system prompt with hard rules?
- When should information live in resources versus tool descriptions versus rules?
- How much context can agents realistically remember and consistently follow?
- What are the best practices for progressive disclosure in MCPs?

After the research, propose a simplification strategy.

I have a strong feeling that the interface exposed to the agent should be much simpler—almost like a system prompt:

- If frontend task → bootstrap.
- If greenfield → do A, B, C.
- If redesign → do X, Y, Z.
- Before implementation → collect required evidence.
- Before claiming done → verify.

Simple, deterministic, and difficult to ignore.

However, don't implement anything yet.

First:
1. Research best practices.
2. Compare them against our current coordination layer.
3. Identify where we're likely over-complicating things.
4. Propose a simplified design.
5. Create a temporary experimental branch where we simplify only the agent-facing interface (not the internal intelligence).
6. Run the same frontend tasks before and after the simplification and compare:
   - MCP tool usage
   - Workflow adherence
   - UI quality
   - Number of ignored recommendations
   - Overall agent behavior

Only if the simplified version consistently performs better should we replace the current coordination layer.

The goal is to make the MCP internally powerful but externally extremely easy for an AI agent to understand and follow.

The MCP is excellent at preventing fake “UI done” claims and grounding design work in screenshots, shortlists, and verify gates. It is weaker as a low-friction coding companion: payloads are huge, ceremony is sticky, and some audits measure token math more than taste. Best used for redesigns and shipping gates — not every 10-line CSS tweak.
How the interaction felt
Working with Frontend Perception MCP felt like pairing with a strict design QA lead who also carries a clipboard of process gates. When the face card was followed (`card.next`, `owed`, section checklist), progress was orderly: borrow inspiration, lock components, pull resources, implement, then prove it visually. When the envelope ballooned — duplicated coordinator prose, 100KB+ JSON, inspiration session errors — the agent spent more time decoding the MCP than improving the product.
